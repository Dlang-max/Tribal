# Concurrent Codex Knowledge Curation Implementation Plan

> **For agentic workers:** Use superpowers:subagent-driven-development. Implementors author production code, independent testers author tests, and separate reviewers review each track. Work in separate Git worktrees with focused descriptive commits.

**Goal:** Run concurrent server-side Codex curators over project Markdown KBs, with five internal tools, SeaweedFS/MySQL storage, optional OpenAI embeddings, and a realtime React graph.

**Architecture:** One local unauthenticated project server hosts two public MCP tools, a run-token-protected internal MCP endpoint, graph JSON, and an SSE activity stream. Each request starts a separate noninteractive Codex process; actual KB operations publish observable events. Markdown is stored as immutable SeaweedFS objects and MySQL publishes current revisions; only publication is coordinated, not entire curator runs.

**Tech Stack:** Existing Python 3.12/FastMCP/PyYAML plus FastAPI, uvicorn, httpx, boto3, PyMySQL; existing React/TypeScript/Vite/React Flow design. OpenAI `text-embedding-3-small` is optional until `OPENAI_API_KEY` is supplied.

**Spec:** `agent-knowledge-base/mcp-interface-v1.md`, `agent-knowledge-base/specs/v1/*.md`, and the user's concurrent named-curator/live-GUI requirements in this session.

## Global constraints

- Preserve the original checkout and its existing uncommitted changes. Integration worktree starts from snapshot `40666a6` and has its own branch.
- All new source is under `src/`, tests under `tests/`, container assets under `docker/`. Existing user-authorized validator location is retained.
- Every code file has a top description; every Python function/method/nested helper/fixture/test has a one-line purpose comment before decorators.
- No agents spawn additional agents, edit the sibling vault, or touch another task's files. Each role commits only its own files. Parent integrates reviewed commits.
- No live OpenAI calls or API-key requirement for tests. No secrets committed. Codex authentication is separately configured by the operator.
- Actual SeaweedFS/MySQL adapters are required; tests may inject controlled storage/HTTP/process doubles. Do not silently substitute a production fake KB or simulated curator.
- GUI names/colors/trails identify server-side curator runs. Activity is generated by real tool execution, not model reasoning text.
- Keep the implementation small: one local project process, no Redis, job service, auth system, graph database, or Kubernetes changes.

## Shared interfaces (binding across tasks)

Python package lives at `src/tribal-mcp-server/src/tribal_kb/`; existing `server.py` remains the console entrypoint.

`service.py` exposes `KnowledgeBaseService(project_id, object_store, catalog, embedding_client=None, spec_root=None, validator_path=None)` and async methods:

- `search_notes(query: str, limit: int = 10) -> list[dict]`: results contain `id,title,path,excerpt`; use project-scoped lexical lookup plus compatible vectors when available.
- `read_note(note_id: str) -> dict`: `id,title,type,path,markdown,revision,links`; links contain `id,source,target`.
- `follow_link(source_id: str, target_id: str) -> dict`: verify actual link, return target read result.
- `get_note_spec(note_type: str) -> str`: common+type spec text, closed type allowlist.
- `apply_changes(changes: list[dict], *, request_id: str | None = None, request_hash: str | None = None) -> dict`: result `status,message,notes,issues`; status updated/unchanged/invalid/conflict. Changes use `action` create/update/archive and `path`; create/update include `markdown`, update/archive include integer `expected_revision`. Public notes use `path,action` with created/updated/archived.
- `graph() -> dict`: `project_id,nodes,edges`; nodes contain `id,title,type,path`, edges `id,source,target`. Edge IDs deterministic from source/target IDs.
- `get_request_result(request_id: str, request_hash: str) -> dict | None` and `remember_request_result(request_id: str, request_hash: str, result: dict) -> None`, async; differing payload hash for a used ID is an error. A successful apply stores its actual published outcome so retries after process failure reconcile published changes.

Task A documents injectable object-store/catalog constructors and protocols promptly for its tester. Real adapters are `SeaweedObjectStore` and `MySQLCatalog`. Read-only small object operations may use thread offloading around blocking boto3/PyMySQL. Current-note manifest publication is transactional; uploaded-but-unpublished immutable objects are harmless orphans. Concurrent edits recheck revisions against current published notes, validate the full proposed vault, and publish only valid batches. No embedding calls occur while holding the publication lock. Embeddings never block valid core writes; missing key means lexical-only search with no fabricated vectors.

Task B `runtime.py` exposes `CodexCurator(service, events, *, codex_bin="codex", internal_url, timeout_seconds=300, model=None)` implementing the existing two async Curator protocol methods. Task B may add optional injected subprocess runner/config parameters for controlled tests. It provides `create_app(...)` in `server.py` for ASGI and keeps `create_server(curator=None)` usable for existing callers.

Runtime routes: public `/mcp`, private `/internal/mcp`, `GET /api/graph`, `GET /api/activity`, health `/healthz`. One configured project via `TRIBAL_PROJECT_ID`; ordinary localhost trusted demo only. Internal MCP calls require a cryptographically random, active run token (header `x-tribal-run-token`) and are scoped to that run. Context runs get only the four read tools; update runs can also apply changes. Avoid recursive connections to public MCP.

SSE JSON event envelope: `type,run_id,name,color,message,status,node_ids,edge_ids,timestamp`; types run_started/activity/run_finished/run_failed/graph_changed; statuses working/done/failed. All events identify their curator. Broadcast to every browser subscriber with bounded queues and cleanup; heartbeat and best-effort reconnect behavior. GUI may recover graph from snapshot after reconnect; no durable event-service requirement.

Graph and activity use note IDs; highlight an edge only on verified follow_link. Use a random readable palette color fixed for each run. Node read/search-wrapper events describe observed tool activity; do not display private model reasoning.

## Review focus

1. Concurrent stale writers and invalid cross-note batches must not overwrite newer state or publish partial invalid graphs (A tests).
2. An embedding outage/missing key must preserve committed Markdown and exact/lexical search; incompatible/stale vectors must not rank (A tests).
3. Codex failure/cancellation/timeout, forged internal tokens, read-only run writes, false successful final responses, and duplicate requests must fail honestly without orphan processes (B tests).
4. Two browsers and two overlapping curator runs must receive/retain independent activity; reconnect cannot retain stale highlights or leak subscriptions (B/C tests).
5. Packaging from an installed wheel/container must locate dependencies/contracts, while GUI shows backend failures instead of fake graphs (B/C checks).
