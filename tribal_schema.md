# Tribal Database Schema

Target: **MySQL 9.7**.

This proposed nine-table schema supports shared knowledge documents, revision history, evidence, links, chunks, and embeddings. It has been checked against the MySQL documentation but has not been executed against a MySQL server.

The central design is: **documents have stable identities; revisions preserve content; retrieval data is derived from specific revisions.**

Tribal is domain agnostic. A knowledge base is a named collection of knowledge, and a domain is a subject area within it. Neither implies software, a filesystem workspace, or Git. Notes record relevant working contexts explicitly; a Git repository is one optional context type alongside experiments, datasets, organizations, filesystem resources, and other contexts. Multiple notes in one domain may refer to different contexts, or declare none.

This revision replaces the earlier draft's repository ownership model. It is a proposed schema, not an applied migration. Existing prototypes would need an explicit knowledge-base assignment and migration of Git facts into note contexts; a repository must not be automatically renamed into a knowledge base.

UUIDs are generated by the application, stored as `BINARY(16)`, and exported as strings. All application connections should use UTC.

The companion [Markdown v1 specification](tribal_markdown_spec.md) defines the accepted file format. Accepted canonical files are limited to 8 MiB; decoded summaries and source locators to 8,192 UTF-8 bytes; recorded raw links to 16,384 bytes; parsed link targets to 1,024 code points; and heading anchors to 255 code points. These limits fit the SQL projections below. They are validated before writes and must never be enforced through silent truncation. Use strict SQL mode and client/server packet capacity sufficient for accepted files and derived JSON. See [MySQL string capacities](https://dev.mysql.com/doc/refman/9.7/en/string-type-syntax.html).

## Tables and rationale

| Table | Purpose and rationale |
|---|---|
| `knowledge_bases` | Names an independent knowledge collection and its publication boundary without assuming an external project or repository. |
| `domains` | Organizes knowledge within a knowledge base while allowing links across domains. |
| `documents` | Preserves identity through renames, moves, revisions, and soft deletion. |
| `document_revisions` | Stores complete content snapshots, metadata, authorship, and applicability. |
| `document_sources` | Attaches supporting evidence to a document revision or individual section. |
| `document_links` | Supports navigation and backlinks while preserving unresolved references. |
| `document_chunks` | Makes both short findings and large documents retrievable in focused passages. |
| `embedding_profiles` | Records the model and configuration that define an embedding space. |
| `chunk_embeddings` | Stores vectors separately so models can change without modifying knowledge documents. |

## SQL schema

```sql
CREATE DATABASE tribal
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_0900_ai_ci;

USE tribal;

-- Configure every application connection to use UTC as well.
SET time_zone = '+00:00';


-- ============================================================
-- 1. Knowledge bases
-- ============================================================

CREATE TABLE knowledge_bases (
    id                  BINARY(16) PRIMARY KEY,
    knowledge_base_key  VARCHAR(128) NOT NULL,
    name                VARCHAR(255) NOT NULL,
    description         TEXT NULL,
    created_at          DATETIME(6) NOT NULL
                        DEFAULT CURRENT_TIMESTAMP(6),

    UNIQUE KEY uq_knowledge_base_key (knowledge_base_key)
) ENGINE = InnoDB;


-- ============================================================
-- 2. Domains
-- ============================================================

CREATE TABLE domains (
    id                  BINARY(16) PRIMARY KEY,
    knowledge_base_id   BINARY(16) NOT NULL,
    domain_key          VARCHAR(128) NOT NULL,
    name                VARCHAR(255) NOT NULL,
    description         TEXT NULL,
    created_at          DATETIME(6) NOT NULL
                        DEFAULT CURRENT_TIMESTAMP(6),

    UNIQUE KEY uq_domain_key (
        knowledge_base_id,
        domain_key
    ),

    -- Supports checking knowledge base ownership through composite FKs.
    UNIQUE KEY uq_domain_knowledge_base (
        knowledge_base_id,
        id
    ),

    CONSTRAINT fk_domain_knowledge_base
        FOREIGN KEY (knowledge_base_id)
        REFERENCES knowledge_bases (id)
) ENGINE = InnoDB;


-- ============================================================
-- 3. Documents: stable identity and current state
-- ============================================================

CREATE TABLE documents (
    id                   BINARY(16) PRIMARY KEY,
    knowledge_base_id    BINARY(16) NOT NULL,

    -- Current vault-relative path, including the ".md" extension.
    -- Portable NFC/case-fold collisions are checked under a knowledge base
    -- row lock; this SQL collation alone does not enforce that rule.
    vault_path           VARCHAR(512)
                         COLLATE utf8mb4_0900_bin NOT NULL,

    -- NULL only while creating the initial revision.
    current_revision_id  BINARY(16) NULL,

    created_at           DATETIME(6) NOT NULL
                         DEFAULT CURRENT_TIMESTAMP(6),

    deleted_at           DATETIME(6) NULL,

    UNIQUE KEY uq_document_path (
        knowledge_base_id,
        vault_path
    ),

    UNIQUE KEY uq_document_knowledge_base (
        knowledge_base_id,
        id
    ),

    CONSTRAINT fk_document_knowledge_base
        FOREIGN KEY (knowledge_base_id)
        REFERENCES knowledge_bases (id)
) ENGINE = InnoDB;


-- ============================================================
-- 4. Document revisions: immutable content snapshots
-- ============================================================

CREATE TABLE document_revisions (
    id                   BINARY(16) PRIMARY KEY,
    document_id          BINARY(16) NOT NULL,
    knowledge_base_id    BINARY(16) NOT NULL,
    domain_id            BINARY(16) NOT NULL,

    revision_number      INT UNSIGNED NOT NULL,
    parent_revision_id   BINARY(16) NULL,

    -- Version of Tribal's Markdown schema.
    schema_version       SMALLINT UNSIGNED NOT NULL,

    -- Historical location at the time this revision was created.
    vault_path           VARCHAR(512)
                         COLLATE utf8mb4_0900_bin NOT NULL,

    title                VARCHAR(255) NOT NULL,
    summary              TEXT NOT NULL,

    kind                 ENUM(
                             'finding',
                             'overview',
                             'decision',
                             'procedure',
                             'reference'
                         ) NOT NULL,

    status               ENUM(
                             'active',
                             'superseded',
                             'archived'
                         ) NOT NULL DEFAULT 'active',

    verification_state   ENUM(
                             'unverified',
                             'verified',
                             'disputed'
                         ) NOT NULL DEFAULT 'unverified',

    verified_at          DATETIME(6) NULL,

    -- Domain-specific applicability, e.g. region, population,
    -- date range, experimental conditions, or operating environment.
    scope                JSON NOT NULL,

    -- Explicit external working contexts, defaulted to [] by the API.
    -- Example: [{"key":"trial","type":"experiment",
    --            "locator":"urn:trial:germination-2026"}]
    -- Git metadata belongs in a declared git_repository context.
    contexts             JSON NOT NULL,

    -- Arrays of strings.
    tags                 JSON NOT NULL,
    aliases              JSON NOT NULL,

    -- Canonical authored document, including YAML frontmatter.
    markdown             LONGTEXT NOT NULL,

    -- SHA-256 of the exact stored Markdown's UTF-8 bytes.
    content_hash         BINARY(32) NOT NULL,

    author_type          ENUM(
                             'human',
                             'agent',
                             'system'
                         ) NOT NULL,

    author_id            VARCHAR(255) NOT NULL,
    change_summary       TEXT NULL,

    created_at           DATETIME(6) NOT NULL
                         DEFAULT CURRENT_TIMESTAMP(6),

    UNIQUE KEY uq_document_revision_number (
        document_id,
        revision_number
    ),

    UNIQUE KEY uq_revision_document (
        document_id,
        id
    ),

    KEY ix_revision_domain (
        domain_id,
        kind,
        status
    ),

    FULLTEXT KEY ft_revision_description (
        title,
        summary
    ),

    -- The document must belong to the supplied knowledge base.
    CONSTRAINT fk_revision_document
        FOREIGN KEY (knowledge_base_id, document_id)
        REFERENCES documents (knowledge_base_id, id),

    -- The domain must belong to that same knowledge base.
    CONSTRAINT fk_revision_domain
        FOREIGN KEY (knowledge_base_id, domain_id)
        REFERENCES domains (knowledge_base_id, id),

    -- A parent revision must belong to the same document.
    CONSTRAINT fk_revision_parent
        FOREIGN KEY (document_id, parent_revision_id)
        REFERENCES document_revisions (document_id, id),

    CONSTRAINT chk_revision_number
        CHECK (revision_number > 0),

    CONSTRAINT chk_schema_version
        CHECK (schema_version > 0),

    CONSTRAINT chk_verified_timestamp
        CHECK (
            verification_state <> 'verified'
            OR verified_at IS NOT NULL
        ),

    CONSTRAINT chk_scope_object
        CHECK (JSON_TYPE(scope) = 'OBJECT'),

    CONSTRAINT chk_contexts_array
        CHECK (JSON_TYPE(contexts) = 'ARRAY'),

    CONSTRAINT chk_tags_array
        CHECK (JSON_TYPE(tags) = 'ARRAY'),

    CONSTRAINT chk_aliases_array
        CHECK (JSON_TYPE(aliases) = 'ARRAY'),

    CONSTRAINT chk_summary_capacity
        CHECK (OCTET_LENGTH(summary) <= 8192),

    CONSTRAINT chk_markdown_capacity
        CHECK (OCTET_LENGTH(markdown) <= 8388608)
) ENGINE = InnoDB;


-- Added after document_revisions exists because the tables
-- reference one another. This also checks revision ownership.

ALTER TABLE documents
    ADD CONSTRAINT fk_document_current_revision
    FOREIGN KEY (id, current_revision_id)
    REFERENCES document_revisions (document_id, id);


-- ============================================================
-- 5. Sources: evidence extracted from a revision
-- ============================================================

CREATE TABLE document_sources (
    id                   BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    revision_id          BINARY(16) NOT NULL,

    -- NULL means the source applies to the whole document.
    section_anchor       VARCHAR(255) NULL,

    -- Extensible domain-neutral classification; validated by the API.
    source_type          VARCHAR(64) NOT NULL,

    -- File path, URL, document UUID, or another source identifier.
    locator              TEXT NOT NULL,

    -- Optional reference to contexts[].key on this source revision.
    -- JSON context membership is validated by the API.
    context_key          VARCHAR(128) NULL,

    -- Source-specific version: edition, release, entry ID, timestamp,
    -- or Git object ID only when the declared context is Git.
    source_revision      VARCHAR(255) NULL,

    -- Source-specific information such as method, edition, page,
    -- observation time, symbol, line range, outcome, or reviewer.
    details              JSON NULL,

    KEY ix_source_revision (
        revision_id,
        section_anchor
    ),

    CONSTRAINT fk_source_revision
        FOREIGN KEY (revision_id)
        REFERENCES document_revisions (id),

    CONSTRAINT chk_source_locator_capacity
        CHECK (OCTET_LENGTH(locator) <= 8192)
) ENGINE = InnoDB;


-- ============================================================
-- 6. Links: outgoing references and backlink lookup
-- ============================================================

CREATE TABLE document_links (
    id                   BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    source_revision_id   BINARY(16) NOT NULL,

    -- Occurrence order within the source document.
    ordinal              INT UNSIGNED NOT NULL,

    source_anchor        VARCHAR(255) NULL,

    -- Original syntax, including aliases and unresolved references.
    raw_link             TEXT NOT NULL,

    -- Parsed target name or path, excluding its anchor.
    target_text          VARCHAR(1024) NOT NULL,
    target_anchor        VARCHAR(255) NULL,

    -- NULL when missing or ambiguous.
    target_document_id   BINARY(16) NULL,

    UNIQUE KEY uq_link_occurrence (
        source_revision_id,
        ordinal
    ),

    KEY ix_link_target (
        target_document_id
    ),

    CONSTRAINT fk_link_source
        FOREIGN KEY (source_revision_id)
        REFERENCES document_revisions (id),

    CONSTRAINT fk_link_target
        FOREIGN KEY (target_document_id)
        REFERENCES documents (id),

    CONSTRAINT chk_raw_link_capacity
        CHECK (OCTET_LENGTH(raw_link) <= 16384)
) ENGINE = InnoDB;


-- ============================================================
-- 7. Chunks: focused retrieval units
-- ============================================================

CREATE TABLE document_chunks (
    -- Published chunk identity is immutable. Rechunking allocates new IDs.
    id                   BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    revision_id          BINARY(16) NOT NULL,

    -- Position within the revision's chunk sequence.
    ordinal              INT UNSIGNED NOT NULL,

    -- Example: ["Architecture", "Startup sequence"].
    heading_path         JSON NOT NULL,

    section_anchor       VARCHAR(255) NULL,
    content              MEDIUMTEXT NOT NULL,

    -- Half-open byte range [start_byte, end_byte)
    -- within the canonical UTF-8 Markdown.
    start_byte           INT UNSIGNED NOT NULL,
    end_byte             INT UNSIGNED NOT NULL,

    chunker_version      VARCHAR(32) NOT NULL,

    UNIQUE KEY uq_chunk_position (
        revision_id,
        ordinal
    ),

    FULLTEXT KEY ft_chunk_content (
        content
    ),

    CONSTRAINT fk_chunk_revision
        FOREIGN KEY (revision_id)
        REFERENCES document_revisions (id),

    CONSTRAINT chk_chunk_range
        CHECK (end_byte > start_byte),

    CONSTRAINT chk_heading_path_array
        CHECK (JSON_TYPE(heading_path) = 'ARRAY'),

    CONSTRAINT chk_chunk_capacity
        CHECK (OCTET_LENGTH(content) <= 8388608),

    CONSTRAINT chk_chunk_end
        CHECK (end_byte <= 8388608)
) ENGINE = InnoDB;


-- ============================================================
-- 8. Embedding profiles: immutable model configurations
-- ============================================================

CREATE TABLE embedding_profiles (
    id                   BINARY(16) PRIMARY KEY,
    profile_key          VARCHAR(128) NOT NULL,

    provider             VARCHAR(128) NOT NULL,
    model                VARCHAR(255) NOT NULL,
    model_version        VARCHAR(128) NULL,

    dimensions           SMALLINT UNSIGNED NOT NULL,

    -- Input templates, normalization, distance metric,
    -- output dimensions, and other model settings.
    configuration        JSON NOT NULL,

    created_at           DATETIME(6) NOT NULL
                         DEFAULT CURRENT_TIMESTAMP(6),

    UNIQUE KEY uq_embedding_profile_key (
        profile_key
    ),

    UNIQUE KEY uq_embedding_profile_dimensions (
        id,
        dimensions
    ),

    CONSTRAINT chk_profile_dimensions
        CHECK (dimensions BETWEEN 1 AND 16383),

    CONSTRAINT chk_embedding_configuration_object
        CHECK (JSON_TYPE(configuration) = 'OBJECT')
) ENGINE = InnoDB;


-- ============================================================
-- 9. Chunk embeddings: vectors generated from chunk inputs
-- ============================================================

CREATE TABLE chunk_embeddings (
    chunk_id             BIGINT UNSIGNED NOT NULL,
    profile_id           BINARY(16) NOT NULL,
    dimensions           SMALLINT UNSIGNED NOT NULL,

    -- Capacity accommodates profiles with different dimensions.
    embedding            VECTOR(16383) NOT NULL,

    -- SHA-256 of the exact text submitted to the embedding model.
    input_hash           BINARY(32) NOT NULL,

    created_at           DATETIME(6) NOT NULL
                         DEFAULT CURRENT_TIMESTAMP(6),

    PRIMARY KEY (
        chunk_id,
        profile_id
    ),

    KEY ix_embedding_reuse (
        profile_id,
        input_hash
    ),

    CONSTRAINT fk_embedding_chunk
        FOREIGN KEY (chunk_id)
        REFERENCES document_chunks (id),

    -- Checks that the declared dimensions match the profile.
    CONSTRAINT fk_embedding_profile
        FOREIGN KEY (profile_id, dimensions)
        REFERENCES embedding_profiles (id, dimensions),

    -- Checks that the actual vector matches those dimensions.
    CONSTRAINT chk_embedding_dimensions
        CHECK (VECTOR_DIM(embedding) = dimensions)
) ENGINE = InnoDB;
```

## Design rationale

### Stable identity makes the knowledge graph durable

A document's UUID identifies it independently of its title, domain, and filename. Renaming "Authentication startup" therefore does not create a different knowledge object. Links resolve to document IDs while retaining their original Markdown syntax.

### Knowledge organization is independent of working context

`knowledge_bases` and `domains` organize subjects such as botany, operations, history, or authentication. `document_revisions.contexts` records what a particular note was working with, and `scope` records where its claims apply. Context keys are local to a revision; `document_sources.context_key` points into that declared list and the API rejects dangling keys. No repository table, Git checkout, remote URL, branch, or commit is required to create a knowledge base, domain, or note.

When a note records work in Git, it explicitly declares a `git_repository` context identifying that repository; known branch/commit details are recorded there. A source can select that context and optionally pin its own revision. The service must not infer these facts from its current directory, a note's domain, or the location of the exported vault. Filesystem and other non-Git context profiles remain equally valid, and unknown context/source types are preserved under the generic contract.

The selected context determines a source revision's namespace independently of source type. A dataset or publication explicitly tracked in Git uses a Git object ID for `source_revision`, with release/edition labels retained in `details`; without a Git context, those versions remain opaque strings. Filesystem locators denote directory roots even without trailing slashes; relative source paths append beneath the full root. Git locators instead identify a repository tree plus relative path and revision, not an HTTP file-base URL. The Markdown specification defines the exact root/profile validation rules.

### Revisions preserve history and support concurrent editing

Each revision contains the complete authored document and its metadata. An agent can inspect what changed, retrieve an older version, or identify the revision behind a particular finding. The current revision pointer makes ordinary reads straightforward.

The composite foreign keys enforce that parent and current revisions belong to the correct document and that domains belong to the correct knowledge base. Explicit unique referenced keys follow [MySQL 9.7's foreign-key requirements](https://dev.mysql.com/doc/refman/9.7/en/create-table-foreign-keys.html).

### Canonical Markdown supports human editing and portability

Keeping the complete original document preserves content and frontmatter beyond the fields Tribal currently understands. Extracted columns make that content searchable without parsing Markdown on every query. Import/export must still define identity handling, link rewriting, and conflict detection; the database alone cannot guarantee round-trip consistency.

### Chunks support both small findings and large documents

A finding may produce one chunk; an overview may produce many. Heading paths preserve context, and revision ownership prevents retrieval from mixing passages from different document versions. Full-text indexes support lexical search on descriptions and passages. See the [MySQL full-text documentation](https://dev.mysql.com/doc/refman/9.7/en/fulltext-restrictions.html).

### Separate sources make evidence inspectable

An agent can retrieve a claim together with the files, tests, or discussions supporting it. Section anchors allow evidence to support a specific part of a large overview.

### Separate embeddings make retrieval replaceable

The same chunk can have embeddings from multiple profiles while a new model is evaluated or introduced. Profile and input hashes allow reuse when the embedding input is unchanged. MySQL's native `VECTOR` type stores the numeric values; the dimension constraints prevent incompatible shapes. See the [MySQL VECTOR documentation](https://dev.mysql.com/doc/refman/9.7/en/vector.html).

Query embeddings must use a compatible profile with the stored embeddings. Matching dimension counts alone does not establish compatibility. A deterministic embedding input can combine document title, heading hierarchy, and chunk content; `input_hash` covers that complete input. Embeddings are derived data and do not need to appear in the Obsidian Markdown export.

### Typed columns and JSON serve different needs

Identity, ownership, document kinds, and lifecycle states have explicit columns and constraints. Scope and source-specific details remain flexible. Frequently searched JSON properties may eventually need dedicated columns or indexes.

## Application responsibilities

- **Atomic writes:** After acquiring the knowledge base lock, lock affected documents, check the writer's expected revisions, insert new revisions and their sources, links, and chunks, then update current pointers and paths in one transaction.
- **Knowledge base serialization:** Before document locks or database-dependent validation, acquire the owning `knowledge_bases` row with `SELECT ... FOR UPDATE`. All knowledge-state mutations, including deletes/restores, chunk replacements, and embedding-result publication, use this gate. Repeat preflight checks using current reads under the lock. Operations spanning knowledge bases lock those rows in UUID order, followed by documents in UUID order. Model calls and external checks run outside the transaction; external working contexts are not publication-lock boundaries.
- **Portable paths:** Compare `NFC(casefold(NFC(path)))` using Unicode 15.1 full default case folding. Check the complete final namespace, including soft-deleted reservations, while holding the knowledge base lock. Exclude a moved document's own old reservation. The SQL case-sensitive unique key remains an additional exact-path guard; it is not a substitute for the portable comparison.
- **Immutability:** Content revisions and embedding-profile configurations are append-only through the API. The DDL does not itself prevent updates.
- **Metadata consistency:** Extracted fields must agree with canonical Markdown. JSON checks validate broad shapes, not every nested property.
- **Explicit contexts:** Validate context key uniqueness, source context membership, and known context-profile fields. Relative file/code evidence needs a declared resource root. Git-specific checks apply only to a declared `git_repository` context; there is no implicit repository, branch, commit, or working directory. Other source revisions remain opaque identifiers. Context/source types are extensible and unknown profiles retain their data with disclosed unchecked semantics.
- **Verification quality:** Setting `verified` requires adequate recorded evidence. The database only enforces the timestamp requirement.
- **Retrieval scope:** Default searches use current revisions of undeleted, active documents and compatible embedding profiles. Applicability must also be checked.
- **Link resolution:** Resolve targets by the supported Markdown and Obsidian rules. Preserve missing and ambiguous references. Derived target IDs can be updated when references become resolvable without changing the authored revision.
- **Link publication:** Creates, content/heading edits, moves, deletes, restores, and purges recompute all current internal-link occurrences from nondeleted source documents in the knowledge base against the final namespace, including unchanged sources outside the batch. Missing or ambiguous document targets clear cached target IDs; missing headings retain a unique document ID with a diagnostic. Publish bindings and coherent diagnostics with document heads in the same commit. Read graph/export data through one committed snapshot and current-head joins. Historical source revisions are not rebound by this refresh.
- **Embedding generation:** Embeddings can be generated asynchronously. A missing embedding row means that chunk is not yet available for that profile.
- **Deletion policy:** Soft deletion preserves history and links. In this schema, deleted documents retain their reserved vault paths; permanent purging requires explicit dependency handling.

### Atomic batches and path swaps

An import batch validates every selected file and planned final ID/path assignment before publishing any head changes. If any selected write fails, the complete batch rolls back. The knowledge base lock also covers namespace effects on unchanged documents.

MySQL checks unique constraints during statements, so a collision-free final path swap cannot be applied as naive sequential renames. After checking all expected revisions and final reservations, stage every moved existing document at `.tribal-staging/<document-uuid>.md` inside the same transaction, then assign final paths and insert newly created documents. This root prefix is reserved and cannot be authored. Historical revision paths contain only final paths. Temporary paths must never commit, appear in an export, or create extra revisions. Readers must not use dirty reads. See [MySQL unique constraints](https://dev.mysql.com/doc/refman/9.7/en/constraint-primary-key.html).

### Rechunking and asynchronous embeddings

The unique `(revision_id, ordinal)` key intentionally represents one published chunk set per revision. Published chunk inputs are immutable; a replacement set receives fresh IDs rather than updating content, ranges, heading context, or version in place.

Compute replacement passages outside locks. Under the knowledge base lock, check the expected old chunk IDs/version, delete dependent embedding rows before old chunk rows, insert the complete new set, and commit. Readers see a complete old or new set. Do not reset IDs with `TRUNCATE`. Rechunking changes derived records without adding an authored revision.

Embedding jobs carry the exact chunk ID, profile ID, and input hash. Before publishing, acquire the knowledge base lock, check that the original chunk still exists, verify its immutable profile, and reconstruct the expected input hash. Discard stale results; never attach them to another chunk by ordinal. A missing row for an oversized input remains an explicitly diagnosed unavailable embedding, not a truncated vector input.

### Lexical search behavior

Default InnoDB full-text indexing omits tokens shorter than three characters and configured stopwords; its default parser also does not supply CJK word segmentation. Therefore `FULLTEXT` alone does not promise reliable lookup of terms such as `Go`, `CI`, or `IO`. Deployments must disclose their parser, minimum/maximum token sizes, stopword settings, and any index rebuild needed after configuration changes. See [MySQL full-text parsing](https://dev.mysql.com/doc/refman/9.7/en/fulltext-natural-language.html).

V1 lexical search must expose a `literal` mode that checks the entire query as a literal case-sensitive substring against current eligible document titles, summaries, and chunk content. SQL implementations must apply `COLLATE utf8mb4_0900_bin` to literal comparisons rather than inherit the text columns' case-insensitive collation. Bind SQL parameters and escape `LIKE` metacharacters; `%` and `_` in a literal query are not wildcards. Default search must use this fallback when full-text search has no searchable tokens or returns no hits. The response must state the applied mode and whether a result window is paginated; it must not silently discard part of the candidate corpus. This simple knowledge base-scoped fallback supports short terms and CJK substrings without requiring a new index type. Large deployments may optimize it while preserving its declared semantics.

Identifier and path lookups use their explicit fields and resolution rules rather than relying on a full-text index.

## Conformance fixtures

The [Markdown v1 review-edge fixtures](fixtures/markdown_v1/README.md) specify complete file snapshots, canonical hashes, graph outcomes, path-only and batch-swap revisions, serialized collision outcomes, and stale embedding-job handling. They are design acceptance data; neither an importer nor the DDL has been exercised against MySQL by those fixture-integrity checks.

## Vector search availability

Vector storage does not imply indexed similarity search. MySQL 9.7's built-in `DISTANCE()` function is available only in MySQL HeatWave on OCI and MySQL AI. With Community Edition, Tribal would need application-side similarity computation or an additional vector-search component. See [MySQL vector-function availability](https://dev.mysql.com/doc/refman/9.7/en/vector-functions.html).
